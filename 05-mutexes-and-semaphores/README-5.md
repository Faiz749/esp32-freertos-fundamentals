# Day 5: FreeRTOS Mutexes and Semaphores

## Project Description

This project demonstrates how a FreeRTOS mutex can protect shared data when multiple tasks access the same global variable.

Two FreeRTOS tasks increment the same global counter. Before either task changes the counter, it must first take the mutex.

Only one task can hold the mutex at a time. After the task finishes using the shared counter, it gives the mutex back so the other task can access the protected data.

The Serial Monitor is used to observe the counter values generated by both tasks.

## Components Used

* ESP32 38-pin board
* USB cable
* Serial Monitor

## Shared Variable

The shared variable used by both tasks is:

```cpp
int counter = 0;
```

Both Task 1 and Task 2 modify this global counter.

## Mutex

The mutex is declared using:

```cpp
SemaphoreHandle_t counterMutex;
```

It is created inside `setup()` using:

```cpp
counterMutex = xSemaphoreCreateMutex();
```

Before modifying the shared counter, each task attempts to take the mutex:

```cpp
xSemaphoreTake(counterMutex, portMAX_DELAY)
```

After the protected work is complete, the task gives the mutex back:

```cpp
xSemaphoreGive(counterMutex);
```

## Task Structure

### Task One

Task One:

* Takes the mutex.
* Increases the shared counter.
* Prints the new counter value.
* Gives the mutex back.
* Waits for 500 milliseconds.
* Repeats continuously.

### Task Two

Task Two:

* Takes the same mutex.
* Increases the same shared counter.
* Prints the new counter value.
* Gives the mutex back.
* Waits for 500 milliseconds.
* Repeats continuously.

## Concepts Learned

* Understanding why shared data needs protection
* Creating a FreeRTOS mutex
* Using `SemaphoreHandle_t`
* Using `xSemaphoreCreateMutex()`
* Taking a mutex with `xSemaphoreTake()`
* Releasing a mutex with `xSemaphoreGive()`
* Using `portMAX_DELAY` to wait for a mutex
* Checking for successful mutex access using `pdTRUE`
* Protecting a global variable from simultaneous task access
* Understanding that a mutex provides safe access but not a fixed task order
* Using `vTaskDelay()` and `pdMS_TO_TICKS()`
* Running multiple tasks with the same priority

## Output

Example Serial Monitor output:

```text
Mutex created successfully
Task 1 Counter: 1
Task 2 Counter: 2
Task 1 Counter: 3
Task 2 Counter: 4
Task 1 Counter: 5
Task 2 Counter: 6
```

The exact task order may change depending on the FreeRTOS scheduler.

For example, Task 2 may sometimes access the mutex before Task 1.

The important behavior is that only one task can modify the protected counter at a time.

## Mistakes Fixed

* Added a mutex to protect the shared counter.
* Used the same mutex for both FreeRTOS tasks.
* Used `xSemaphoreTake()` before modifying the shared variable.
* Used `xSemaphoreGive()` after the protected work was completed.
* Kept `vTaskDelay()` outside the protected section so the mutex is not held while a task is sleeping.
* Checked whether the mutex was successfully created.
* Used `pdTRUE` to confirm successful mutex access.
* Used a larger task stack size for additional memory headroom.

## Embedded Systems Relevance

Mutexes are important in embedded systems where multiple tasks may need access to the same data or hardware resource.

Examples include shared sensor information, Serial communication, displays, communication buses, and system-state variables.

Using a mutex prevents multiple tasks from entering the same protected section at the same time, helping avoid race conditions and making shared-resource access safer and more controlled.
